# PHASE 1: BIG PICTURE

## 1. Plain-English Summary

Finding graduate scholarships is genuinely hard — hours of searching obscure university pages, verifying deadlines, checking eligibility, writing tailored SOPs. Students either miss opportunities or apply blindly with generic essays.

This is an **autonomous 5-agent AI pipeline** that automates the entire process end-to-end. Upload your resume → system scrubs private data → five specialized AI agents take over: one enriches your profile (including GitHub), one searches the web for opportunities, one fetches and audits real university pages, one scores and ranks the top 5 using a deterministic formula, one drafts a personalized SOP. Runs in under 3.5 minutes, no human in the loop, using real APIs (Gemini, Tavily) and a production-grade resilience stack.

## MODULE 1 — Domain Layer (`domain/`)

**What it is:** Pure Python, zero I/O, zero network, fully deterministic. 177 unit tests. Every rule about what makes a "good" match lives here. Think of it as the rules engine in a chess program — it defines what moves are legal and how pieces score, without touching the board.

---

### `domain/pii.py` — Privacy by Design

**What it does:** Before any text touches Gemini/Tavily/logs, `PIIScrubber.scrub()` strips PII in this exact order:

```
1. Display name      (case-insensitive whole-word regex)
2. Email addresses
3. Aadhaar-like IDs  ← MUST run before phone (phone regex is broader)
4. Passport-like IDs
5. SSN-like IDs
6. Phone numbers     ← after Aadhaar so digits are already masked
7. Name-containing URLs
```

`PIIVault` stores originals keyed by placeholder: `store("name", "Rahul Sharma")` → `[CANDIDATE_NAME]`. At the end, `rehydrate(sop_text)` swaps placeholders back — *locally, never sent to LLM*.

**Analogy:** A coat-check. Your coat (real name) stays at the door. You get a ticket. The LLM only sees the ticket.

**Top 3 interview questions:**

> **Q: "Why does Aadhaar scrubbing run before phone?"**
> A: The phone regex is intentionally broad to catch international formats. A 12-digit Aadhaar `1234 5678 9012` would match the phone pattern and get `[REDACTED_PHONE]` instead of `[REDACTED_ID]`. Running Aadhaar first masks those digits before phone regex sees them.

> **Q: "What if the TTL expires while the SOP is being rendered?"**
> A: `rehydrate()` checks `if self.is_expired: return text`. Placeholders stay in output unchanged instead of crashing. Safe degradation, never a 500 error.

> **Q: "What if a name appears inside a LinkedIn URL?"**
> A: Step 7 — a URL regex is built dynamically from the display name slug, catching `https://linkedin.com/in/rahulsharma`, replacing with `[REDACTED_URL]`.

### `domain/gpa.py` — Multi-Scale GPA Normalization

**Four strategies selected by `profile_enricher` based on LLM-extracted `cgpa_scale`:**

| Strategy | Trigger | Details |
|---|---|---|
| `passthrough` | scale == 4.0 | already US scale, identity |
| `indian_to_us` | scale == 10.0 | breakpoint lookup table |
| `percentage_to_us` | scale == 100.0 | breakpoint lookup table |
| `bavarian` | any other | `1 + 3×(G_max−G_student)/(G_max−G_min)` |

Each returns a `GPAResult` with a `confidence` float (passthrough=1.0, indian_to_us=0.60). This confidence flows into scoring.

**Top 3 interview questions:**

> **Q: "Why breakpoint tables instead of linear formulas for Indian GPA?"**
> A: Indian CGPA is non-linear — the gap from 8.5→9.0 is harder to earn than 4.5→5.0. A linear formula would map 8.0/10 → 3.2/4.0, underselling it; the breakpoint table maps it to 3.7, matching how US admissions actually interprets Indian transcripts.

> **Q: "What is the Bavarian formula?"**
> A: Standard German conversion: `N = 1 + 3×(G_max - G_student)/(G_max - G_min)`. Closer to max grade = closer to 1.0 (best in Germany). Used as general-purpose converter for non-standard scales.

> **Q: "Can a student game their score by lying about GPA scale?"**
> A: Yes — known limitation. LLM extracts `cgpa_scale` from resume text with no cross-validation against institutional registries. All conversions are labelled as "estimates" in the UI. Future improvement: integrate Anabin database or similar.

### `domain/scoring.py` — Composite Scoring Engine

```
total = (academic_fit    × 0.25)
      + (field_alignment  × 0.25)   ← only LLM-sourced component
      + (funding_strength × 0.20)
      + (feasibility      × 0.20)
      + (evidence_conf.   × 0.10)
```

**Critical rule:** `has_blocking_unmet=True` → score hard-capped at 25.0. A citizenship failure cannot be overcome by perfect scores elsewhere.

**Tiebreaker:** total desc → evidence_confidence desc → deadline_distance_days asc.

**Top 3 interview questions:**

> **Q: "Why is field_alignment only 25% if it's arguably the most important factor?"**
> A: Field alignment is the ONLY LLM-sourced component — a soft judgment. At 50%, a hallucinated 1.0 could rank a completely ineligible opportunity first. At 25%, deterministic factors (GPA, funding, evidence) act as a sanity check on the LLM's fuzzy judgment.

> **Q: "What does evidence_confidence represent?"**
> A: `VerificationResult.completeness_score` from Source Auditor — the fraction of key fields (name, funding, deadline, institution) that were successfully span-verified against the official page. All verified = 1.0. Nothing confirmed = 0.0.

> **Q: "Why is the cap at 25.0 specifically?"**
> A: Approximately the score a candidate gets with zero fit across every dimension. Ensures a blocked opportunity ranks below any viable-but-imperfect one.

### `domain/span_verifier.py` — Stage-1 Anti-Hallucination

**What it does:** The LLM in Source Auditor extracts text like `"deadline: March 15, 2025"`. The span verifier checks: is this exact phrase actually in the fetched page?

**Normalization pipeline applied to BOTH span and page text:**
1. Unicode NFKC (ligatures ﬁ→fi, full-width Ａ→A)
2. Casefold (handles German ß etc.)
3. Smart quote → ASCII straight quote
4. Em/en dash → ASCII hyphen
5. Whitespace collapse

Then: `norm_page.find(norm_span)`. Found → `matched=True`. Not found → field demoted to `UNVERIFIED`, drops `evidence_confidence`.

**Top 3 interview questions:**

> **Q: "Why exact substring instead of fuzzy matching?"**
> A: Fuzzy matching needs a threshold and could accept "stipend: $50,000" when the page says "stipend: $5,000" — a 1-char typo changing meaning dramatically. Exact substring after normalization is conservative. False negatives (LLM paraphrases) are acceptable; false positives (accepting hallucinated facts) are not.

> **Q: "What does NFKC normalization do?"**
> A: Converts Unicode compatibility variants to canonical form. Without it, a PDF-extracted "ﬁeld" (ligature fi) wouldn't match an LLM-extracted "field" — identical content, different bytes.

> **Q: "Why the 15–400 character bounds?"**
> A: Below 15 chars: too short, could match anywhere by coincidence ("PhD", "2025"). Above 400 chars: LLM is just copying a paragraph — not evidence of a specific fact, expensive to verify.

### `domain/claim_verifier.py` — Stage-2 Anti-Hallucination

**3 deterministic guards per SOP sentence:**

```
Guard 1: Referential Integrity
  → every cited fact_id must exist in the allowed-fact pack

Guard 2: Numeric Token Guard
  → every number in the sentence must appear in cited facts
  → "My GPA of 3.9" needs a fact containing "3.9"

Guard 3: Proper-Noun Allow-List
  → multi-word Title Case phrases must match cited facts or be [CANDIDATE_NAME]
  → "I studied at Imperial College London" needs a fact with "Imperial College London"
```

Failing sentence → one LLM repair attempt → still failing → **stripped entirely**.

**Top 3 interview questions:**

> **Q: "Could the LLM bypass the ledger by not citing any fact IDs?"**
> A: Guard 1 only fires on cited IDs. But Guards 2 and 3 run regardless. A number like "3.9" or proper noun "MIT" not in the fact pack will fail Guards 2 or 3 and trigger repair/strip no matter what.

> **Q: "What's in the allowed-fact pack?"**
> A: Built from verified opportunity data (institution, funding, deadline, requirements) and candidate profile (education, skills, GPA, projects). A flat dict: `{FACT_001: "University of Toronto", FACT_002: "$25,000 stipend", ...}`. The LLM is given this pack and told to use only these facts.

> **Q: "What if too many sentences get stripped?"**
> A: No automatic coherence check — known limitation. A future improvement: if >30% of sentences stripped, regenerate from scratch with stricter instructions. For now, SOP degrades gracefully (shorter but accurate) rather than hallucinating.

## MODULE 2 — Resilience Stack (`resilience/`)

**What it is:** A **6-layer decorator chain** wrapping every external API call. Instead of each adapter having its own try/except/retry/cache, call `decorate(fn, cfg)` once and get a bulletproof wrapper.

**Analogy:** Each layer is a car safety system — ABS, airbags, crumple zones. They don't affect normal driving but activate automatically on failure.

---

### `resilience/middleware.py` — The Composition Root

**Execution order inside `_wrapped()` on every call:**
1. Check request cache (per-run, in-memory) → return if hit
2. Check TTL cache (cross-run) → return if hit
3. `QuotaGovernor.acquire()` → sleep or raise
4. `CircuitBreaker.is_open()` → fast-fail if open
5. `with_retry(with_timeout(fn))` → actual call with backoff + deadline
6. `CircuitBreaker.record_success/failure()` → update state
7. Write to both caches
8. Append `UsageRecord` (telemetry)

**Top 3 interview questions:**

> **Q: "Why is Telemetry the outermost layer if it records latency — doesn't that miss cache hits?"**
> A: It records ALL calls including cache hits — that's exactly what you want. Cache hits have near-zero latency and outcome `"cache_hit"`. If Telemetry were innermost, you'd only see cache misses, which is incomplete observability.

> **Q: "What's the difference between TTLCache and RequestCache?"**
> A: TTLCache is cross-run — Tavily search results from a previous run reused if valid. RequestCache is per-run — if the same URL is fetched twice in one run, the second hits the in-run cache. Two-level caching avoids redundant API calls at different granularities.

> **Q: "What happens if both the primary LLM and its circuit breaker are open?"**
> A: The breaker raises `QuotaExhaustedError` from inside the middleware. The `_CompositeLLMPort` in `composition.py` sits above the middleware, catches that error, and routes the call to the failover adapter (Groq) which has its own separate breaker stack.

---

### `resilience/breaker.py` — 4-State Circuit Breaker

```
CLOSED       → normal operation
  |  (3 consecutive failures)
OPEN         → fast-fail all calls; wait cooldown_s (30s)
  |  (cooldown elapsed)
HALF_OPEN    → allow one probe call
  |success → CLOSED     |failure → OPEN or KNOWN_EXHAUSTED
KNOWN_EXHAUSTED → daily quota spent OR model retired (404)
```

**The 4th state** is unique. Standard 3-state breakers reset after cooldown regardless of why they tripped. But a daily API quota doesn't reset in 30s. KNOWN_EXHAUSTED prevents pointless probe calls for hours.

**Top 3 interview questions:**

> **Q: "Why a 4th state?"**
> A: Standard OPEN resets after 30s regardless of cause. Daily API quotas reset at midnight. A retired model (404) should never be retried. KNOWN_EXHAUSTED handles both cases without blocking the breaker in OPEN for hours.

> **Q: "How does OPEN auto-promote to HALF_OPEN without a background timer?"**
> A: The `state` property is computed lazily on every access. It checks `time.monotonic() - _opened_at >= cooldown_s`. No background thread needed — promotion happens the first time `is_open()` is called after cooldown expires.

> **Q: "What if a rate limit has a short retry hint — does the breaker trip?"**
> A: Explicitly not. Rate limits with `retry_after <= 8.0s` are handled by the QuotaGovernor's token bucket (which sleeps). Only long rate limits (>8s) increment the failure counter. This prevents false trips on normal API bursting.

---

### `resilience/quota.py` — Token-Bucket QuotaGovernor

**Three mechanisms per provider/model:**

1. **RPM Token Bucket** — fills at `rpm/60` tokens/sec. If empty, waits up to `max_wait_s=8s`; if longer → raise `RateLimitedError` (triggers failover, not a block).
2. **RPD Hard Ceiling** — if `daily_used >= effective_rpd` → raise `QuotaExhaustedError`. Effective = `rpd × (1 - 0.30)` for public runs (30% reserved for judges).
3. **DEC-1 Reasoning Cap** — at the 5th reasoning-tier call → raise `QuotaExhaustedError("Reasoning-tier cap reached")`.

**Top 3 interview questions:**

> **Q: "Why does the token bucket wait instead of immediately failing?"**
> A: The bucket smooths bursting. Sleeping up to 8s lets normal pacing recover without a failover. Beyond 8s, the wait is too long for a real-time pipeline — failover is better than a 30-second stall.

> **Q: "What is the judge reserve ratio?"**
> A: At a hackathon demo with multiple judges simultaneously, public runs could exhaust daily quota before judges get to demo. 30% reserve is held back from public runs so judges always have headroom.

> **Q: "How do you prevent the RPD counter resetting in a long-running process?"**
> A: It doesn't — known limitation. `_daily_used` is an in-memory dict accumulating for process lifetime. Production fix: midnight cron reset, or Redis with TTL-based counters.

## MODULE 3 — Engine (`engine/`)

### `engine/graph.py` — LangGraph StateGraph

**Why LangGraph over alternatives:**
- LangChain LCEL chains: linear only, no conditional branching
- Celery/RQ: overkill for in-process, adds broker dependency
- Raw asyncio.gather: no graph semantics, no state management

**The 3 routing predicates — pure Python, no LLM:**

```python
_r1_enough_candidates: len(candidates) >= 10 or retry_count >= 1?
    yes -> "source_auditor"    no -> "retry_scout"

_r2_has_opportunities: len(opportunities) >= 1?
    yes -> "ranking_strategist"    no -> "degraded_end"

_r3_sop_needed: top_5 and profile?
    yes -> "application_strategist"    no -> "complete_end"
```

Routing is NEVER delegated to an LLM — prevents infinite loops and structurally invalid transitions.

**Top 3 interview questions:**

> **Q: "Why is the scout retry limited to exactly once?"**
> A: R1 forces progression after one retry regardless of candidate count. Hard guard against infinite loops — agentic systems must have deterministic termination.

> **Q: "What is SwarmState and why is it immutable?"**
> A: A Pydantic model representing complete pipeline state. Nodes return new states via `state.model_copy(update={...})` rather than mutating. Each transformation is traceable, debuggable, replayable.

> **Q: "What happens if Agent A5 crashes?"**
> A: Exception propagates to `RunGateway._run_graph()`, which catches it, publishes `RUN_DEGRADED` (FAILED_SAFE), sets `handle.finished=True`. User still gets Phase A top-5 cards (already streamed via PHASE_A_READY). Partial delivery beats silent failure.

---

### `engine/gateway.py` — RunGateway

**Key design decision:** The graph runs in a **dedicated background OS thread with its own fresh `asyncio` event loop**.

**Why a separate thread?** FastAPI (uvicorn) owns the main event loop. LangGraph creates asyncio tasks internally. Running LangGraph in FastAPI's loop could cause task conflicts or cancellations from FastAPI's request lifecycle. `asyncio.new_event_loop()` in a dedicated thread gives LangGraph its own scheduling domain.

```
Main Thread (FastAPI)          Background Thread (graph)
  |                                 |
  GET /events?cursor=5         asyncio.new_event_loop()
  bus.since(5) <---deque<---- bus.publish(event)
                (threading.Lock guards all access)
```

**Top 3 interview questions:**

> **Q: "Why not `asyncio.run_in_executor` instead of a manual thread?"**
> A: `run_in_executor` uses the main loop's thread pool — LangGraph's async internals would still try to schedule on the calling loop, causing conflicts. A fresh `asyncio.new_event_loop()` gives LangGraph its own isolated scheduling domain.

> **Q: "How does EventBus handle concurrent writes from background thread and reads from main thread?"**
> A: `threading.Lock()` — an OS mutex, not `asyncio.Lock()`. `asyncio.Lock` only works within one event loop. Since publish happens in the background thread's loop and reads happen in FastAPI's loop (different loops), only `threading.Lock` is correct.

> **Q: "What prevents memory growing forever?"**
> A: EventBus is `deque(maxlen=500)` — bounded ring buffer, auto-evicts oldest events. Terminal events are kept in a protected `_terminal` slot so they're never evicted. VaultRegistry.cleanup_expired() removes expired PIIVaults.

---

### `engine/event_bus.py` — Ring Buffer EventBus

Classic producer/consumer with cursor-based subscriptions. Each SSE client tracks its own `cursor` (last `seq` seen). `bus.since(cursor)` returns only events newer than that seq.

The `_terminal` slot is the key insight: if 500 events happen after `RUN_COMPLETED`, the terminal event would be evicted from the ring. The protected slot ensures `since()` always appends the terminal event even if evicted.

## MODULE 4 — Agents (`agents/`)

### `agents/intake.py` — IntakeService

Runs **before** the LangGraph graph fires — not a graph node. Called directly from `composition.start_run_with_intake_async()`.

**Pipeline:** validate (size/MIME) → extract text (PyMuPDF/pypdf) → detect scanned PDF → extract name (regex heuristic, first 5 lines) → scrub PII → extract GitHub username from URLs → return `(IntakeResult, PIIVault)`.

**Top 3 interview questions:**

> **Q: "Why is IntakeService NOT a LangGraph node?"**
> A: Intake must happen before the graph starts — you need scrubbed text to build the graph runner, which is injected with `scrubbed_text` at construction time. Making it a node is chicken-and-egg: the graph needs the text to initialize, but the text comes from running the first node.

> **Q: "What happens with a scanned PDF?"**
> A: `PDFDocumentAdapter` detects scans when extracted text is below `ocr_threshold_chars` (default 50 chars). Falls through to `VisionOCRAdapter` which uses the LLM's vision capability to read page images. A warning is added to `IntakeResult.warnings` for the UI.

> **Q: "What if a .txt resume has no PII to scrub?"**
> A: `file_bytes.decode("utf-8", errors="replace")` — even binary garbage won't crash it. PII scrubbing still runs, finds nothing to replace, returns text unchanged. Zero-side-effect design.

### `agents/profile_enricher.py` — Agent A1

**Key implementation: parallel LLM + GitHub fetch**

```python
llm_task = self._extract_profile(scrubbed_text)    # fire immediately
github_task = self._enrich_github_base(username)   # fire immediately (concurrent)

profile, github_from_llm = await llm_task          # await LLM (~2s)
if github_task:
    github_signals = await github_task             # likely already done (ran in parallel)
```

LLM parsing (~2s) and GitHub API (~1s) run concurrently. Without parallelism: ~3s sequential.

**JSON repair flow:** Strip `<think>...</think>` blocks (Groq emits these) → strip markdown fences → `json_repair()` → `_dict_to_profile()` with per-field try/except.

**Top 3 interview questions:**

> **Q: "What if the LLM misidentifies the GPA scale?"**
> A: Wrong strategy applied. But `normalize_gpa()` has bounds checking — `0 <= cgpa <= scale`. If result is invalid, `ValueError` is caught and logged, `normalized_gpa` stays `None`. Scoring uses neutral 50.0 for academic_fit — degraded but not crashed.

> **Q: "Why is the LLM prompt discipline-agnostic?"**
> A: If the prompt said "extract ML skills," it would bias extraction for CS students and under-extract for biology or law students. "Extract from dedicated Skills sections AND project descriptions" works for any field.

> **Q: "What does `reduce_profile()` do?"**
> A: In `domain/reducers.py` — merges existing profile with newly extracted one. In practice returns the new profile, but the reducer pattern allows future logic to merge partial runs or accumulate signals from multiple agents without duplicating fields.

### `agents/opportunity_scout.py` — Agent A2

One LLM call generates a `SearchPlan` — typically 5 queries with different `intent` values (`program`, `scholarship`, `funder`). Queries Tavily (primary) → Jina (secondary fallback). Deduplicates by canonical URL. Filters 18 aggregator sites (scholarships.com, fastweb.com, etc.) to keep only direct official pages.

**Top 3 interview questions:**

> **Q: "Why Tavily over Google Search API?"**
> A: Tavily is built for AI agents — returns structured results with title, URL, and content snippets already extracted. Google Search API returns raw HTML needing further parsing. Tavily's `search_depth="advanced"` fetches and summarizes full page content.

> **Q: "What is a canonical URL and why deduplicate by it?"**
> A: Many results return the same page with slight URL differences (http vs https, trailing slash, UTM params). `canonicalize_url()` normalizes these to prevent the same page being fetched, extracted, and scored multiple times.

> **Q: "Why is `_ENABLE_QUERY_VARIANTS = False`?"**
> A: Query variants increase coverage but also increase Tavily API cost. Disabled for the hackathon to stay within free-tier limits. Feature flag — easy to enable in production.

### `agents/source_auditor.py` — Agent A3

**Most complex agent.** Wave-pipelined fetching:

```
Wave 1: fetch URLs 0-9 concurrently (max 6 at a time)
        -> batch LLM extract (5 pages per LLM call)
        -> span-verify each extracted field
        -> early stop if >= 20 verified opportunities
Wave 2: fetch URLs 10-19 ...   (max 4 waves)
```

**3-tier fetch chain:** Jina Reader (proxied, clean markdown) → trafilatura (local HTML scraping) → Playwright (JS-rendered pages, FULL profile only).

**Span verification on every field:** name, institution, funding_level, deadline, country, degree_level. Non-matching → `FieldStatus.UNVERIFIED`, drops `evidence_confidence`. Raw page text discarded after extraction (RAM guard).

**Top 3 interview questions:**

> **Q: "Why waves instead of fetching all URLs at once?"**
> A: Fetching 20 URLs at once hits server rate limits and triggers bot-detection. Waves of 6 are conservative enough to avoid blocks while still being much faster than sequential. Early stop at 20 verified means Wave 3/4 are rarely needed.

> **Q: "What happens if a URL returns 404?"**
> A: `FetchChain` catches HTTP errors and returns `FetchedDocument(status_class="error", normalized_text="")`. Auditor skips LLM extraction for error pages. Per-domain circuit breaker (`BreakerRegistry.get_domain()`) tracks repeated failures per domain.

> **Q: "What does `is_listing_page` flag do?"**
> A: Flags pages listing multiple scholarships (e.g., a university's scholarship index). If true, the auditor can follow links to individual pages — `_RECURSIVE_DEPTH=1` controls depth. Limited to 1 level to control cost.

### `agents/ranking_strategist.py` — Agent A4

1. Deterministic tri-state eligibility evaluation (no LLM): `evaluate_gpa_minimum()`, `evaluate_citizenship()`, `evaluate_language_test()` → MET/UNMET/UNKNOWN
2. **ONE batched reasoning-tier LLM call** for field_alignment across all opportunities
3. `compute_composite_score()` per opportunity
4. `rank_opportunities()` → top 5

**Why batch the LLM call?** Without batching: 10 opportunities = 10 LLM calls, burning the entire DEC-1 reasoning budget (4 calls/run max).

**Top 3 interview questions:**

> **Q: "Why REASONING tier for field alignment?"**
> A: Field alignment requires nuanced judgment — "computer vision" skills applying to "robotics" is moderate alignment, not 0 or 1. Fast models produce less calibrated floats. Since this is the only reasoning call in the pipeline, it's the right place to spend the budget.

> **Q: "What if the reasoning cap is already hit before A4 runs?"**
> A: `QuotaGovernor` raises `QuotaExhaustedError`. `_CompositeLLMPort` tries Groq failover. If both exhausted, ranking falls back to `field_alignment=0.5` (neutral) for all — degraded but functional.

> **Q: "How does `derive_gaps()` work?"**
> A: For each UNKNOWN or UNMET result, generates an `ActionableGap` with `field`, `severity` (BLOCKING/MODERATE/LOW), and a human-readable message: "Your GPA 3.2 may be below the stated minimum 3.5." Displayed as actionable advice, not raw rejection flags.

---

### `agents/application_strategist.py` — Agent A5

1. Build allowed-fact pack from top-1 opportunity + candidate profile
2. LLM (FAST tier) drafts SOP using `[CANDIDATE_NAME]` for the applicant
3. `verify_sop()` runs 3 guards per sentence
4. Failing sentences: one LLM repair attempt → still failing → **stripped**
5. `PIIVault.rehydrate()` restores `[CANDIDATE_NAME]` → real name *locally, never sent to LLM*
6. Build `ApplicationPackage` with final SOP + execution checklist

**Why FAST not REASONING for SOP?** SOP is creative writing, not multi-step deduction. REASONING would burn the DEC-1 budget needed for A4's field alignment.

**Top 3 interview questions:**

> **Q: "Why does the SOP prompt tell the LLM not to include fact citations like [FACT_001] in output?"**
> A: Citations are verification metadata, not user-facing content. The claim verifier runs on the raw LLM output before rendering. Users see clean prose; citations exist only for the verification pipeline.

> **Q: "Is this SOP usable for a real application?"**
> A: As a first draft — yes. As a final submission — needs human review. The anti-hallucination system guarantees factual accuracy (no invented scores or institutions), but tone, motivation, and specific program knowledge still need editing. The README acknowledges this.

> **Q: "What is the execution checklist?"**
> A: Actionable steps derived from the opportunity's verified requirements — "Request transcripts from [institution]", "Register for IELTS if below [minimum]", "Prepare 2 recommendation letters." Built from verified eligibility data, not LLM-generated.

# PHASE 3: BLIND SPOTS

> These are the parts of the codebase most likely to get you into trouble in an interview. Know these cold — **bring them up yourself before the interviewer does**. It shows maturity and self-awareness, not weakness.

---

## 3.1 — Parts You're Most Likely to NOT Understand

### ❶ `composition.py` — `_CompositeLLMPort` streaming failover bug

In `_CompositeLLMPort.stream()` (lines 440–454), the `_use_failover` flag is **sticky** — once the primary stream fails once, ALL subsequent streaming calls go to failover for the lifetime of the gateway instance. But `complete()` (non-streaming) resets on every call and always tries primary first.

This is **inconsistent behavior** between streaming and non-streaming paths. An interviewer who reads carefully will catch it.

**What to say:** "I noticed the streaming failover is sticky while the complete failover is non-sticky. This is an inconsistency — in production I'd make both non-sticky so the primary can recover after transient failures."

---

### ❷ `engine/gateway.py` — `_run_in_thread` has no cancellation mechanism

Once `threading.Thread` starts, there's no way to force-stop a Python thread mid-execution. `cancel()` in `RunGateway` sets `handle.cancelled = True` and marks `finished = True` — but the background thread **keeps running** until its current awaitable completes naturally.

```python
def cancel(self, run_id: str) -> bool:
    handle.cancelled = True   # flag set
    handle.finished = True    # UI thinks it's done
    # BUT the background thread is still running!
```

This means a "cancelled" run continues consuming API quota and tokens. It just stops reporting to the UI.

**What to say:** "Cancellation is cosmetic — it stops the UI from seeing new events but doesn't stop the background thread. True cancellation would require `asyncio.CancelledError` propagation through the graph runner's tasks, which requires more complex inter-thread signalling."

---

### ❸ `domain/pii.py` — Name extraction heuristic is fragile

`_extract_name()` in `intake.py` uses a simple regex on the first 5 lines: `^([A-Z][a-z]+ ...)$`. It will silently fail for:
- **All-caps names**: "RAHUL SHARMA" → no match
- **Names with particles**: "van der Berg", "al-Hussein" → no match
- **Single-word names**: "Adele" → no match
- **Non-Latin scripts**: "राहुल शर्मा" → no match

If the name isn't extracted, PII scrubbing still runs but won't remove the name. The name could then reach the LLM in the resume text.

**What to say:** "The name extraction heuristic only covers Western name formats. For a globally-targeted product, I'd use a proper NER model or ask the user to confirm their name before processing — which is more reliable and privacy-conscious."

---

### ❹ `resilience/quota.py` — RPD counter never resets

`_daily_used` is an in-memory dict that accumulates for the **entire process lifetime**. A server running for 25 hours would think it's hit the daily limit even after midnight reset. This is acknowledged in a comment but no fix exists.

**What to say:** "The daily quota counter is a known gap — it doesn't reset at midnight. In production I'd use Redis with a key like `quota:gemini:gemini-3.6-flash:{date}` with a 24-hour TTL, giving automatic daily resets."

---

### ❺ `agents/opportunity_scout.py` — Hardcoded domain exclusion list

18 aggregator domains are hardcoded. This list will go stale — new aggregators appear, legitimate sites get blocked. There's no mechanism to update it without a code change.

**What to say:** "The exclusion list is a hardcoded string in source code. Better approach: a config file or database table that ops can update without a deployment. Could also use a domain-classification API."

---

### ❻ `domain/models.py` — Single large file

All Pydantic models — `SwarmState`, `RunMeta`, `Event`, `Opportunity`, `CandidateProfile`, and ~20 others — live in one 800+ line file. The README explicitly notes this is intentional to avoid Pydantic v2 forward-reference issues, but it creates a large, hard-to-navigate file.

**What to say:** "The single models.py was a pragmatic choice to avoid Pydantic v2 circular import issues with forward references. With more time I'd split it into sub-modules using `from __future__ import annotations` and explicit `model_rebuild()` calls."

---

### ❼ `agents/source_auditor.py` — `_WAVE_SIZE=10` but `_MAX_CONCURRENT_FETCHES=6`

These two constants are inconsistent — you try to fetch 10 URLs per wave but limit concurrency to 6. In practice asyncio.gather with semaphore handles this correctly, but the naming is misleading. Someone reading `_WAVE_SIZE=10` expects 10 concurrent fetches, not 6.

## 3.4 — Honest Limitations to Raise Proactively

These are things to **bring up yourself** in an interview. It shows you think like a senior engineer.

**1. No persistent storage — everything is in-memory**
> "Results disappear when the server restarts. A production system needs a database (Postgres or Redis) to persist run results, user sessions, and vault data across restarts."

**2. Single-process, single-node only**
> "The `RunGateway`, `BreakerRegistry`, `QuotaGovernor`, and `PIIVault` are all in-process singletons. Horizontal scaling (multiple server instances behind a load balancer) would break quota tracking and vault lookup. Needs a shared state layer like Redis."

**3. The SOP targets only the #1 ranked opportunity**
> "Currently the Application Strategist generates one SOP for the top-ranked opportunity. Users might want SOPs for all top-5, or a customized version per opportunity."

**4. No deadline staleness check**
> "The pipeline fetches opportunity pages in real time, but if a page says 'applications open January 2025' and today is November 2026, there's no logic to detect that the opportunity has expired. The scoring engine uses `deadline_distance_days` but can't detect past deadlines from text like 'annually in January.'"

**5. GPA normalization has low confidence for non-standard scales**
> "The Bavarian formula has confidence 0.70. For edge cases (French 20-point, Ecuadorian 10-point), the formula may produce an inaccurate US-equivalent GPA. We label it 'estimate' but don't warn the user when confidence is low."

**6. The anti-hallucination system is additive, not causal**
> "The claim verifier ensures numbers and proper nouns in the SOP are grounded in the fact pack. But it doesn't verify that the *relationship* between facts is correct — 'I received a 3.9 GPA from MIT' passes Guards 2 and 3 if both 3.9 and MIT are in the fact pack, even if the candidate actually got 3.9 from IIT Bombay."

**7. No user feedback loop**
> "The pipeline runs once and outputs results. If the user thinks the top-5 is wrong ('I don't want to study in Germany'), there's no way to re-rank or add constraints without re-running the entire pipeline."

## 4.2 — The 5 Hardest Interview Questions (with Model Answers)

---

**Q1: "Why use LangGraph instead of just writing async Python functions with asyncio.gather?"**

> **Model answer:** "LangGraph gives me explicit graph topology as a first-class concept. When I want to say 'if we found fewer than 10 candidates, retry the scout; otherwise proceed to the auditor' — that's a conditional edge in LangGraph. With raw asyncio I'd have to implement that as an if-statement inside an agent, which means the agent has knowledge of the pipeline topology it shouldn't have. LangGraph also gives me typed state (`SwarmState` as a Pydantic model) that flows through every node — each agent receives the full state and returns a new one immutably, making it trivially inspectable and replayable. The alternative is threading mutable state through function arguments, which becomes messy fast. The tradeoff is that LangGraph adds a dependency and has a learning curve — if the pipeline were strictly linear with no branching, I wouldn't need it."

---

**Q2: "Your anti-hallucination system uses substring matching. What if the LLM paraphrases instead of quoting verbatim?"**

> **Model answer:** "That's a real limitation of Stage 1 — the span verifier. If the LLM says 'full scholarship' when the page says 'fully-funded fellowship', the span won't match and the field will be marked UNVERIFIED, which is a false negative. I made this tradeoff deliberately: the alternative is semantic similarity matching, which requires an embedding model, adds latency, and introduces a similarity threshold hyperparameter. More importantly, allowing semantic matches creates a vector for hallucination — 'stipend of $50,000' is semantically similar to 'stipend of $5,000'. The cost of false negatives is lower evidence confidence and a slightly lower composite score. The cost of false positives is recommending an opportunity with wrong facts. I optimized for correctness over recall. In Stage 2 — the claim ledger — I take the same conservative approach: numbers in the SOP must appear literally in the fact pack."

---

**Q3: "How does your system scale to 100 concurrent users?"**

> **Model answer:** "Honestly, it doesn't as-is — and I'd say that directly. The current system has three scale-limiting constraints. First, `RunGateway` is a process-level singleton with an in-memory dict of active runs — horizontal scaling breaks vault lookup and quota tracking. Second, `max_concurrent_runs=3` is a hard cap with no queuing — the 4th concurrent user gets an error. Third, the `QuotaGovernor`'s daily counter is in-memory and resets only on process restart. To scale to 100 concurrent users I'd need: Redis for shared state (run results, vault storage with TTL, quota counters), a proper async task queue (Celery or ARQ) to replace the background thread model, and horizontal scaling behind a load balancer with sticky sessions for SSE streaming. The current design is correct for a hackathon demo; it's the right architecture to evolve from, not the right one to run at scale."

---

**Q4: "How do you know the SOP won't contain hallucinated facts?"**

> **Model answer:** "I can't guarantee it completely — no system can. But I've built two deterministic layers that make it extremely difficult. Stage 1 ensures that every fact the pipeline knows about an opportunity is a verbatim substring of the official page we fetched. So the fact pack itself is grounded in real source documents. Stage 2 then checks every sentence in the SOP against that fact pack: every number (GPA, funding amount, year) must appear in cited facts, every proper noun (institution name, program name) must be in the fact pack. Sentences that fail this check are either repaired with a targeted LLM call that re-grounds the sentence, or stripped entirely. The remaining limitation is relational — the system doesn't verify that facts are correctly associated with each other. If the fact pack contains 'MIT' and '3.9 GPA', the claim 'I got a 3.9 at MIT' passes even if the 3.9 is from IIT Bombay. That's the next improvement: entity-level fact binding rather than token-level matching."

---

**Q5: "What would you change if you had two more weeks?"**

> **Model answer:** "Three things in priority order. First, real user authentication and per-user rate limiting — right now there's a single shared demo password and no isolation between users. I'd add OAuth or API key auth with per-user quota tracking in Redis. Second, persistent run storage — results currently disappear on server restart. I'd add a Postgres layer so users can retrieve previous runs and compare results. Third, I'd fix the SOP to cover all top-5 opportunities, not just the top-1 — users want to apply to multiple programs. Currently the Application Strategist only generates a SOP for rank 1. That's a 2-hour code change but high user value. On the technical debt side, I'd split `domain/models.py` into sub-modules and add integration tests that actually call a sandboxed Gemini endpoint to catch adapter config bugs before production."

## 4.3 — Quick-Fire Concept Questions

These are theory questions on the underlying systems. Have crisp, one-line answers ready.

**LangGraph / Agents**
- *"What is a StateGraph?"* → A directed graph where nodes are async functions and state flows immutably between them via typed Pydantic models.
- *"What is a conditional edge?"* → An edge whose destination is determined at runtime by a routing predicate function — like a switch/case on the current state.
- *"What is the difference between a chain and a graph in LangChain/LangGraph?"* → A chain is a linear sequence. A graph supports branching, loops (with cycle detection), and parallel fan-out.
- *"What is agent tool-calling?"* → Giving an LLM access to typed function signatures it can invoke. Not used here — agents call tools directly in Python, not via LLM tool-calling.

**Resilience Patterns**
- *"What is a circuit breaker?"* → A fault-tolerance pattern that stops calling a failing service after N failures, gives it time to recover, then probes with one request before resuming normal traffic.
- *"What is a token bucket?"* → A rate limiting algorithm where tokens refill at a constant rate and each request consumes one token. If the bucket is empty, requests wait or are rejected.
- *"What is exponential backoff?"* → Retry with increasing delays: wait 1s, then 2s, then 4s. Prevents hammering a struggling service.
- *"What is the difference between RPM and RPD limits?"* → RPM (requests per minute) is a burst-rate limit. RPD (requests per day) is a daily volume ceiling. You can hit RPD without ever exceeding RPM if you make many small requests spread across the day.

**Async Python**
- *"What is `asyncio.wait_for`?"* → A coroutine wrapper that raises `asyncio.TimeoutError` if the wrapped coroutine doesn't complete within N seconds. Used here to enforce phase deadlines.
- *"Why is `threading.Lock` used instead of `asyncio.Lock` in EventBus?"* → `asyncio.Lock` is scoped to a single event loop. Since the EventBus is accessed from two different event loops (FastAPI's and the background thread's), only a thread-safe OS mutex works.
- *"What is a daemon thread?"* → A thread that dies automatically when the main process exits. Used for the background graph runner so it doesn't block server shutdown.
- *"What is `asyncio.new_event_loop()`?"* → Creates a fresh asyncio event loop independent of any existing one. Used to give the background graph runner its own isolated async context.

**Pydantic**
- *"What is `model_copy(update={})`?"* → Creates a shallow copy of a Pydantic model with specified fields replaced. Used for immutable state updates in SwarmState.
- *"What is `pydantic-settings`?"* → Extension that reads field values from environment variables and `.env` files, with type validation. Used for the `Settings` class in `config.py`.
- *"What is `@lru_cache(maxsize=1)` on `get_settings()`?"* → Makes `Settings` a singleton — instantiated once on first call, cached for the process lifetime. Prevents re-reading the `.env` file on every settings access.

**Anti-Hallucination / NLP**
- *"What is NFKC normalization?"* → Unicode compatibility normalization that converts ligatures (ﬁ→fi), full-width characters (Ａ→A), and compatibility variants to canonical ASCII-like forms.
- *"What is casefold vs lower()?"* → `casefold()` is more aggressive than `lower()` — handles special characters like German ß → ss. Better for international text comparison.
- *"What is a proper noun allow-list?"* → A whitelist of common words that look like proper nouns but aren't (e.g., "University", "Department", "Program") — prevents the claim verifier from flagging every academic term as an ungrounded proper noun.

**PDF / Document Processing**
- *"What is the difference between PyMuPDF and pypdf?"* → PyMuPDF (AGPL) is faster and supports OCR via rendering pages as images. pypdf (MIT) is pure Python, slower, but license-compatible for commercial use. This project supports both via a config switch.
- *"What is trafilatura?"* → A Python library that extracts the main article content from an HTML page, stripping navigation, ads, headers, and footers. Better signal-to-noise than raw BeautifulSoup parsing.
